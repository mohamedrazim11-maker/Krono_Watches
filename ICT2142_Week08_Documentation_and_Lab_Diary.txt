1. DATABASE SCHEMA ARCHITECTURE & ERD SPECIFICATIONS (MILESTONE 1)
================================================================================

1.1 Relational Architecture & Cardinality:
--------------------------------------------------------------------------------
The Week 08 target architecture establishes the persistent database as the single
source of truth. Frontend state may cache or display data, but all mutations are
validated and persisted through backend services.

Required Relationships:
1. One User can place Many Orders (1 : M).
   Foreign key: orders.user_id -> users.id (ON DELETE SET NULL).
2. One Order contains Many Order Items (1 : M).
   Foreign key: order_items.order_id -> orders.id (ON DELETE CASCADE).
3. Each Order Item references One Product (M : 1).
   Foreign key: order_items.product_id -> products.id (ON DELETE RESTRICT).
4. Stock reduction occurs strictly upon confirmed order submission / payment workflow.

Entity-Relationship Diagram (Mermaid Representation):
+---------------------+              +-----------------------+
|        USERS        | 1          M |        ORDERS         |
+---------------------+--------------+-----------------------+

1.2 Table Specifications (PostgreSQL DDL / supabase_schema.sql):
--------------------------------------------------------------------------------
1. USERS Table:
   - id (TEXT, PK): Primary key identifier (e.g. 'usr-admin-01', 'usr-1789451291557').
   - user_id (TEXT): Virtual alias matching id for legacy compatibility.
   - full_name (TEXT NOT NULL): Client or administrator full name.
   - email (TEXT NOT NULL UNIQUE): Case-insensitive unique login identifier.
   - password_hash (TEXT NOT NULL): Salted Bcrypt (cost factor 10) password hash.
   - role (TEXT NOT NULL DEFAULT 'customer'): Access tier ('customer' | 'admin').
   - phone (TEXT): Primary contact telephone.
   - address (TEXT): Residential delivery destination.
   - status (TEXT DEFAULT 'Active Member'): Account validity state.
   - created_at (TIMESTAMPTZ DEFAULT NOW()): Registration timestamp.

2. PRODUCTS Table:
   - id (TEXT, PK): Unique product identifier (e.g. 'prod-1', 'prod-rolex-submariner').
   - product_id (TEXT): Virtual alias matching id.
   - name (TEXT NOT NULL): Commercial watch model name.
   - brand (TEXT NOT NULL): Manufacture (Rolex, Omega, Patek Philippe, Krono Swiss).
   - category (TEXT NOT NULL): Horological segment (Luxury, Automatic, Sport, Smart).
   - price (NUMERIC NOT NULL): Authoritative boutique retail price in LKR.
   - old_price (NUMERIC): Pre-discount retail price for promotion calculations.
   - stock_qty (INTEGER DEFAULT 12): Active vault inventory units available.
   - stock_count (INTEGER DEFAULT 12): Backward-compatible inventory column.
   - is_active (BOOLEAN DEFAULT true): Safe-deactivation flag (soft-delete).
   - is_featured (BOOLEAN DEFAULT false): Homepage showcase flag.
   - image_url (TEXT NOT NULL): Primary high-resolution watch asset URI.
   - images (TEXT[]): Array of secondary showcase image URIs.
   - movement (TEXT): Movement calibre specification (e.g., 'Swiss ETA 2824-2').
   - case_material (TEXT): Horological alloy (e.g., '316L Stainless Steel').
   - water_resistance (TEXT): Certified depth rating (e.g., '100m (10 ATM)').

3. ORDERS Table:
   - id (TEXT, PK): Unique order reference (e.g. 'KR-1031', 'KR-799175').
   - order_id (TEXT): Virtual alias matching id.
   - user_id (TEXT FK): References users(id) ON DELETE SET NULL.
   - customer_name (TEXT NOT NULL): Recipient client name.
   - customer_email (TEXT NOT NULL): Delivery notification email.
   - customer_phone (TEXT): Insured courier contact number.
   - delivery_address (TEXT NOT NULL): Physical destination in Sri Lanka.
   - total_amount (NUMERIC NOT NULL): Server-recalculated gross total in LKR.
   - subtotal (NUMERIC NOT NULL): Recalculated item subtotal in LKR.
   - discount_amount (NUMERIC DEFAULT 0): Verified promotional deduction.
   - status (TEXT DEFAULT 'Pending'): Order lifecycle state ('Pending' | 'Paid' |
     'Processing' | 'Shipped' | 'Completed' | 'Cancelled').
   - payment_method (TEXT DEFAULT 'payhere'): Gateway method ('payhere' | 'wire' | 'cod').
   - payment_status (TEXT DEFAULT 'pending'): Settlement state ('pending' | 'completed').
   - created_at (TIMESTAMPTZ DEFAULT NOW()): Order placement timestamp.

4. ORDER_ITEMS Table:
   - id (TEXT, PK): Item row identifier (e.g. 'item-1031-1').
   - order_item_id (TEXT): Virtual alias matching id.
   - order_id (TEXT NOT NULL FK): References orders(id) ON DELETE CASCADE.
   - product_id (TEXT NOT NULL FK): References products(id) ON DELETE RESTRICT.
   - quantity (INTEGER NOT NULL DEFAULT 1): Number of units purchased.
   - unit_price (NUMERIC NOT NULL): Verified unit price captured at checkout time.
   - created_at (TIMESTAMPTZ DEFAULT NOW()): Record creation timestamp.

2.2 Cart-to-Order Persistence & Anti-Tamper Security (Milestone 3):
--------------------------------------------------------------------------------
The checkout workflow enforces server-side validation to guarantee financial and
inventory data integrity:

Step 1 - Cart Validation:
Each item submitted from the frontend is cross-referenced with the database:
- Confirms product existence in active inventory.
- Validates that requested quantity does not exceed available 'stock_qty'.
- Rejects invalid IDs or oversold units with HTTP 400.

Step 2 - Server-Side Order Recalculation:
The server DOES NOT trust the client-provided 'total_amount' or 'subtotal':
```typescript
let calculatedSubtotal = 0;
for (const item of rawItems) {
  const dbProduct = db.products.find(p => p.id === item.product_id);
  const authoritativeUnitPrice = Number(dbProduct.price);
  calculatedSubtotal += authoritativeUnitPrice * item.quantity;
}
const calculatedGrandTotal = Math.max(0, calculatedSubtotal - discountAmount);
```

Step 3 - Multi-Entity Atomic Persistence:
1. An entry is created in the ORDERS table saving user_id, verified total, and status.
2. Individual cart lines are normalized and inserted into the ORDER_ITEMS table
   referencing both the parent order_id and product_id.

Step 4 - Vault Inventory Deduction:
Upon confirmed order placement, product stock is decremented immediately:
```typescript
dbProduct.stock_qty = Math.max(0, dbProduct.stock_qty - item.quantity);
dbProduct.stock_count = dbProduct.stock_qty;
dbProduct.in_stock = dbProduct.stock_qty > 0;
```

Step 5 - Customer Confirmation & Profile Association:
The customer receives an authoritative order confirmation showing their order ID
(e.g., KR-1031). The order is permanently linked to their user account and remains
accessible in /profile across sessions and re-logins.

5. SECURITY ARCHITECTURE & ROLE-BASED ACCESS CONTROL (RBAC) (MILESTONE 4)
================================================================================

5.1 Multi-Layer Defense-in-Depth Architecture:
--------------------------------------------------------------------------------
Securing administrative operations is not restricted to merely hiding buttons on the
frontend. A three-tier access control flow is strictly enforced:

Layer 1 - Server-Side Edge Proxy / Middleware (`frontend/middleware.ts`):
- Intercepts all requests matching `/admin/:path*`.
- Checks for presence of JWT cookie (`krono_token`) or Authorization Bearer header.
- Decodes and inspects the token payload.
- Verifies that token has not expired (`exp * 1000 > Date.now()`).
- Checks user role:
  * If role === 'admin': grants pass-through (`NextResponse.next()`).
  * If role !== 'admin' (customer account): immediately redirects to home page with
    `?error=admin_forbidden` and access denied message.
  * If unauthenticated: redirects to `/login?returnUrl=/admin&unauthorized=true`.

Layer 2 - Administrative Client Layout Guard (`frontend/app/admin/layout.tsx`):
- React hook `useAuth()` monitors client authentication state.
- If an unauthorized user bypasses client caching, useEffect forces immediate navigation:
  `router.push("/?error=admin_forbidden")`.

Layer 3 - Server Route Guard Helper (`frontend/lib/server/auth.ts`):
- The `requireAdmin(req)` helper verifies JWT signature on privileged mutating API routes
  (e.g., DELETE /api/products/[id], PATCH /api/orders/[id]/status).
- Returns HTTP 401 Unauthorized or HTTP 403 Forbidden with structured error payloads.

6.1 Debugging Case 1: Next.js Edge Runtime Cryptography Incompatibility
--------------------------------------------------------------------------------
- Symptom / Issue:
  When configuring server-side route protection in `frontend/middleware.ts` for Next.js,
  importing Node.js `jsonwebtoken` or `crypto` threw runtime exceptions:
  `Dynamic Code Evaluation / Node.js crypto module is not supported in Edge Runtime`.
  This prevented the middleware from executing and caused 500 errors on protected routes.

- Root Cause Analysis:
  Next.js middleware runs on the V8 Edge Runtime environment by default, which lacks
  access to Node.js core libraries (like `crypto.createHmac`) bundled inside the legacy
  `jsonwebtoken` package.

- Implementation & Resolution:
  Implemented a lightweight, Edge-compatible base64url JWT decoder function directly
  within `middleware.ts`. This extracts `sub`, `role`, and `exp` without external binary
  dependencies:
  ```typescript
  function decodeJwtPayload(token: string): { role?: string; exp?: number } | null {
    try {
      const parts = token.split(".");
      if (parts.length !== 3) return null;
      const base64 = parts[1].replace(/-/g, "+").replace(/_/g, "/");
      const jsonPayload = decodeURIComponent(
        atob(base64)
          .split("")
          .map((c) => "%" + ("00" + c.charCodeAt(0).toString(16)).slice(-2))
          .join("")
      );
      return JSON.parse(jsonPayload);
    } catch {
      return null;
    }
  }
  ```
  Full HMAC signature validation is maintained on Node.js API routes via `requireAdmin()`,
  achieving both sub-millisecond Edge middleware route filtering and robust cryptographic
  integrity.


6.2 Debugging Case 2: Client Price Tampering & Cart Validation Desynchronization
--------------------------------------------------------------------------------
- Symptom / Issue:
  During simulated integration testing of Milestone 3, a malicious client payload could
  theoretically send altered `unit_price` or `total_amount` values in the checkout POST
  request (e.g., setting a 385,000 LKR luxury watch to 100 LKR). The initial backend
  handler trusted `orderData.total_amount` without verifying item prices against the
  database.

- Root Cause Analysis:
  The initial `createOrder` method accepted the client's payload directly to calculate
  subtotals, violating the fundamental architectural rule of Week 08 (Slide 7: "Important:
  do not trust totals sent by the browser. Recalculate order totals on the server using
  product data from the database.").

- Implementation & Resolution:
  Refactored `createOrder` in `frontend/lib/server/db.ts` to implement a strict 5-step
  server-side verification protocol:
  1. Iterate through `orderData.items` and query each product by ID from the database.
  2. Overwrite any incoming price with `Number(dbProduct.price)` from the persistent store.
  3. Validate `stock_qty >= requestedQty` before processing.
  4. Sum the verified prices on the server to compute the true subtotal and total.
  5. Atomically decrement `stock_qty` in the database and write normalized records to
     both ORDERS and ORDER_ITEMS tables.
  Any price mismatch or tampering attempt is neutralized, guaranteeing 100% financial
  and inventory data consistency.
